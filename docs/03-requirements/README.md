# Requirements

Requirements translate the brief and discovery findings into a clear statement of what the product must do, how well it must do it, and which constraints must be respected.

## Objectives

- Define functional requirements
- Define non-functional requirements
- Separate must-have needs from optional ideas
- Record accessibility, security, privacy, SEO and performance expectations
- Make scope testable before design and development begin

## Inputs

- Client brief
- Discovery findings
- Known constraints
- Existing systems and integrations
- User needs and business goals

## Outputs

- `requirements.md`
- Prioritised requirement list
- Acceptance criteria
- Dependencies and constraints
- Explicit out-of-scope items

## Principles

Requirements should describe outcomes and behaviour rather than prematurely prescribing implementation.

Use identifiers where practical so requirements can be referenced in UX, issues, tests and pull requests.

Mark assumptions and unresolved requirements clearly rather than hiding uncertainty.

## Exit Criteria

Move to UX when:

- [ ] Core functional requirements are documented
- [ ] Non-functional requirements are documented
- [ ] Accessibility requirements are documented
- [ ] Security and privacy requirements are documented where relevant
- [ ] Performance and SEO expectations are documented where relevant
- [ ] Requirements are prioritised
- [ ] Acceptance criteria exist for critical requirements
- [ ] Dependencies and constraints are known
- [ ] Out-of-scope items are explicit
- [ ] Major requirement conflicts are resolved or recorded
